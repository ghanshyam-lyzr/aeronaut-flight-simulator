# Browser-local landing history

Flight log now keeps the last 20 finished landing missions and crosswind-practice attempts alongside the existing time/distance log. Each row has the observed outcome, completion date (including year, time and time zone), aircraft, airfield/runway and exercise. Native disclosure rows expose the reason, available touchdown measurements, crosswind feedback and the captured setup. Aircraft and airfield filters combine; changing one preserves keyboard focus.

The history is explicitly local to this browser origin, separate from public rankings and not a verified score. It never contacts an online service. It is an arcade simulator's observations, not flight-training certification.

## Collection and persistence

- `Activities` takes an optional `LandingHistory` observer. The browser attaches it; ranked simulations do not. Landing/crosswind starts take a fresh attempt id and a detached setup snapshot. No changes to landing grades, physics, replay rules or ranked-v1.
- After the controllers process a physics slice, a finished landing is captured before the result UI. The id is consumed before persistence, so repeated finished slices, pause, result redraws and failed writes cannot add another record. A boundary check before retry/cancel/switch also captures a terminal result before controllers clear it. An unfinished attempt is discarded.
- Crosswind borrows the wind and runway before capture of its initial setup; its outcome and feedback are captured before releasing that wind. Ordinary landings preserve actual wind snapshots at **start and finish**, with their transition flags, rather than assuming the selected preset or a calm default. These are endpoint snapshots, not a wind replay.
- Aircraft id/name, field id/name/runway/heading/size/elevation/surface, initial power/flaps/gear/assist/pose/trim/airspeed, mission targets, light preset, dates, elapsed simulation time and available touchdown/feedback values are retained. Start time is a wall-clock date; duration is simulation time, excluding pauses.
- Schema: `aeronaut-landing-history` contains `{version:1, attempts:[...]}`, newest completion first. Stored distances/altitudes use metres, speeds/sink/wind use m/s, angles use radians **except touchdown alignment, which the controller already supplies in degrees**. Times are seconds and dates canonical ISO strings. UI conversions label kt, fpm, m, ft MSL, degrees, seconds and percent. Centreline/threshold signs retain left/right, bank retains left/right and pitch retains nose up/down.
- Every optional metric is strictly numeric, finite and bounded. Missing/damaged values become `null` and display `Unavailable`, including a completely missing touchdown. Unknown identities remain unknown. No measurements, dates or aircraft labels are substituted from the current flight. Stored text is length-bounded and escaped at rendering.
- The loader validates the version and root, skips malformed entries, deduplicates ids and keeps the first 20 usable records. Corrupt JSON, old/future schemas and blocked reads safely produce empty history without rewriting on load. Writes validate again and use settings' `browserStorage()` boundary. Quota/read/write/property-access failures never escape into the simulator; completed records stay in session memory with an explicit persistence warning. Opening Flight log or leaving retries a failed write. Reload persistence requires working storage.
- The existing `aeronaut-flights` key, ten-second eligibility, time/distance totals and previous-flight rows are preserved. No database, sign-in, network dependency or new package is added.

## Verification

`npm test`: **797 passing**, including 14 landing-history tests. `npm run build`: passes with the existing large-chunk warning. Focused tests run real reference-physics landing and crosswind approaches through `Activities`, then compare stored touchdown values directly with the controller's observations. Coverage includes success, failed touchdown, failure before touchdown, under-ten-second attempts, per-retry identities, the 20-entry bound, cancellation/switching/unsupported starts/external reset, repeated result rendering, every storage boundary, later-write recovery, partial/old/corrupt records, safe text rendering, filters, and preservation of existing flight totals.

An isolated Chromium check also exercised the actual browser app's `flight`, `activities`, `landing` and `landingHistory`: Playwright appended test-only references to the served main-module response (no diagnostic hook added to production). The existing deterministic feedback pilot flew a successful crosswind approach using ordinary inputs through those real controllers. The result UI appeared and exactly one crosswind attempt was persisted. Pause/resume and two logbook renders retained one row; retry followed by switching to the jet retained the original trainer record once. A pre-existing 120-second / 1 NM flight remained intact. There were no page errors or external requests.

## Responsive evidence

The app was served on port 5173 via `forge serve`. Chromium used low quality and a reduced canvas pixel ratio for this VM's software renderer. The UI stayed at normal CSS scale. Measured at 1600×900, 1280×800 and 390×844: dialog content widths 818 / 818 / 356 px, no horizontal overflow, sticky close control visible. Filters returned 2 of 4 trainer attempts; combining trainer with Orvane returned the empty-filter message. A focused selector retained focus after filtering. Native summaries expanded by keyboard/click; both missing and observed measurements were inspected.
